Objectif : contrairement à la passe 2026-05-28 (cohérence interne), cette passe évalue le L3 sous trois lentilles **produit** : (1) simplifier le travail des utilisateurs, (2) transformer la connaissance en capital cognitif qui se compose dans le temps, (3) identifier une ou deux features « frontier ». Elle intègre le cadrage infra du 2026-07-03.

## 0. Contexte nouveau (2026-07-03)

- **v1.0.0 déployée en prod BNP** ; le chemin de query prod s'arrête à L2 (`server/query/router.py` → `aquery_llm`). **L3 est dormant** : deps installées dans l'image (`Dockerfile:45-47`), `TwinRAGEngine` importé par aucun entrypoint ni par `server/` (grep zéro hit, confirmé 2026-07-03).
- **Serving prod = LLM as a Service BNP** (gpt-oss-120b aujourd'hui, migration imposée vers Gemma 4 31B-it — les deux validés groupe). Contrat L3 compatible : `chat.completions`, JSON mode sur 6/7 appels, `reasoning_effort` en `extra_body` (à vérifier : ignoré proprement par le serving Gemma, sinon micro-patch pour le rendre conditionnel).
- **2× NVIDIA L40S attribuées** aux fonctions Intelligence, cadrées **accélérateurs R&D/innovation pour les KB** — pas du serving prod. Principe : bench iso-modèle avec la cible LLMaaS (Gemma 4 31B FP8) pour que les résultats se transfèrent.

## TL;DR

Le L3 est une **chaîne de traitement de requête** bien construite (intent → reason → act → observe, dégradation gracieuse partout) mais c'est un **système sans mémoire** : rien de ce qui se passe à l'usage (questions, échecs, feedback, citations) n'est persisté ni réinjecté. La connaissance ne se compose pas — elle est consommée. Les trois leviers de cette passe :

1. **Simplifier** : faire porter par L3 les choix aujourd'hui laissés à l'utilisateur (mode retrieval, expansion, folder), streamer la synthèse, rendre les dégradations visibles au lieu de silencieuses.
2. **Capitaliser** : fermer la boucle usage→connaissance. Persister traces + feedback, transformer les non-réponses en backlog de « dette de connaissance », faire vivre thesaurus et ontologie depuis l'usage réel (la moitié de la boucle existe déjà : `query_expander` v2 lit `Onto_{ws}`).
3. **Frontier** : le **Curateur nocturne** (batch GPU qui propose chaque matin tags rétroactifs, fusions d'entités, docs à revalider, FAQ candidates — tout en human-in-the-loop via les workflows d'approbation existants) et la **mémoire organisationnelle multimodale** (Gemma 4 vision : schémas, captures, tableaux deviennent citables).

## Axe 1 — Simplifier le travail des utilisateurs

### U1 — L'utilisateur porte des choix que le code sait faire (S2)

`lightrag_mode="hybrid"` est une constante (`config.py:81`, `act.py:66-68`) alors que le L3 calcule déjà un intent (F05), un domaine (REASON) et un routing folder (F06, keyword-based). Côté WebUI, le panneau Retrieval expose mode/top_k/min_score — des paramètres d'expert que la population cible (opérateurs IT, pas des praticiens RAG) n'a pas à comprendre. **Reco** : un sélecteur de mode automatique (règles simples d'abord : entité nommée → local, question de synthèse → global, défaut hybrid), mode manuel conservé en « avancé ». C'est le seul chaînon manquant de l'UC « Query Intelligence » — le reste existe. CONFIRMÉ (constante + code F05/F06 présents).

### U2 — Pas de streaming en L3 : activer tel quel = régression UX (S1 si activation)

Aucun `stream=True` dans le package (grep zéro hit, confirmé). Le chat prod actuel streame (`/twin/api/query/stream`). La latence perçue L3 = intent + reason + rerank + **synthèse complète** (2 048 tokens, effort high) — plusieurs secondes de silence. **Reco** : streamer au minimum l'appel de synthèse (OBSERVE) et pousser des événements de phase (« recherche… », « synthèse… ») dans l'intervalle ; les 3 appels amont sont courts (80-500 tokens). À traiter comme prérequis d'activation, pas comme optimisation.

### U3 — Dégradations silencieuses : l'utilisateur reçoit du moins bon sans le savoir (S2)

Chaque étage dégrade gracieusement (`try/except` → fallback : question brute comme search_query, top-K brut sans rerank, etc.) — excellent pour la robustesse, mais aucun signal ne remonte. Une réponse produite en mode dégradé est indistinguable d'une réponse nominale. **Reco** : projeter `QueryTrace` (early_exit, fallbacks activés) dans la réponse API et un indicateur discret côté UI — cohérent avec la sémantique `answer_status` déjà exposée par L2 et avec le chantier error-UX (PR #350). CONFIRMÉ (fallbacks aux sites listés dans l'inspection 2026-07-03 ; aucun champ de statut dégradé dans `QueryResult`, `models/schemas.py:64-69`).

### U4 — La continuité conversationnelle existe mais est bridée (S3)

REASON fait la coréférence avec 10 messages d'historique tronqués à 500 chars (`reason.py:163-169`, `config.py:72`) ; la synthèse n'en voit que 3 × 200 chars (`observe.py:120-131`). Suffisant pour « et sur la version 12 ? », insuffisant pour un fil de diagnostic long. **Reco** : ne pas gonfler les fenêtres à l'aveugle — mesurer d'abord sur traces réelles (cf. K1) la longueur utile des fils, puis ajuster. INFÉRÉ (limite fonctionnelle non mesurée).

### U5 — La curation est 100 % manuelle alors que les workflows d'approbation existent déjà (S2)

L'opérateur saisit tags, folders, review à la main ; le package ne propose rien à l'ingestion (constat « UC3 absent » de l'inspection : les settings `indexing_*` sont du code mort, `config.py:39-43`). Or toute l'infrastructure de validation humaine est déjà livrée côté produit (tags governance request/approve, notifications, activity, review queue). **Reco** : l'Ingestion Intelligence R&D (GPU) doit produire des **propositions pré-remplies dans ces workflows existants** — jamais d'auto-application. Ça réduit le travail utilisateur sans toucher à la doctrine de validation humaine (Manu 2026-05-22, Fabrice 2026-05-26).

### U6 — Les réponses scriptées sont hardcodées en français dans le code (S4)

Réponses OOS/greeting/malicious en dur (`engine.py:329-350`). Fonctionnel, mais wording non gouverné (pas aligné sur la passe error-UX) et non localisable. **Reco** : externaliser dans un asset JSON de copy, même mécanique que le mapping d'erreurs frontend.

## Axe 2 — Transformer la connaissance en capital cognitif

Le diagnostic central : **le système répond mais n'apprend rien de ses réponses.** Tout ce qui suit vise à fermer des boucles.

### K1 — Le feedback et les traces sont jetés : la fuite de capital n°1 (S1)

`features/feedback.py` est un buffer **in-memory, non persisté, branché nulle part** (constat 05-28 réconfirmé) ; `QueryTrace` (latence, requête résolue, termes d'expansion, compteurs, early_exit) meurt avec la requête ; `FeedbackEntry.query_trace_id` est une string libre sans génération d'ID stable (05-28 §TL;DR-7, toujours vrai). Chaque 👍/👎, chaque question reformulée, chaque échec est de la **connaissance sur la connaissance** — perdue. **Reco (préalable à tout le reste de l'axe)** : ID de trace UUID généré, persistance `QueryTrace` + `FeedbackEntry` dans Memgraph (labels dédiés `Trace_{ws}`/`Feedback_{ws}`, workspace-scopés comme le reste), reliés aux docs/chunks cités. Anonymisation : le fingerprint HMAC des users existe déjà (`engine.py:39-50`) — l'étendre à la persistance. Décision PO associée : rétention (RGPD).

### K2 — Les non-réponses sont le signal le plus précieux et ne sont capturées nulle part (S1)

Une question OOS confiance ≥ 0.85, une réponse `no-context` (L2), un « insufficient information » textuel de synthèse : autant de **trous de la KB constatés par les utilisateurs eux-mêmes**. Aujourd'hui : réponse d'excuse, fin. **Reco** : un **gap ledger** — chaque non-réponse persiste (question anonymisée, folder, date, fréquence) et alimente une vue steward « dette de connaissance » triée par récurrence, avec notification (canaux notifications/activity déjà livrés). C'est la matérialisation du « Uber de la connaissance » validé par Manu : la demande insatisfaite pilote l'offre documentaire.

### K3 — La boucle auto-renforçante ontologie↔usage existe à moitié et est éteinte (S2)

Le chemin retour est déjà codé : `query_expander` v2 traverse `Onto_{ws}` (SYNONYM/RELATED_TO/CO_OCCURS 2-hops, `ontology/storage.py:257-278`) pour enrichir les requêtes. Mais (a) la feature est off par défaut (`enable_ontology=False`, `ontology.json` absent = disabled by design), (b) l'ontologie ne se nourrit que des documents (DSEP), jamais de l'usage. **Reco** : activer la boucle sur un folder pilote, et nourrir DSEP des **traces de requêtes** (K1) : les termes fréquents sans match thesaurus/ontologie sont les meilleurs candidats synonymes — c'est l'usage qui découvre le vocabulaire réel des utilisateurs, pas les documents. Préalable technique : `OntologyNode.properties` est perdu à la persistance (le MERGE ne le projette pas, 05-28 §1.3) — à corriger avant d'investir le graphe.

### K4 — Le thesaurus est un capital figé de 50 termes (S3)

`it_ops_thesaurus.json` : 50 entrées statiques, embarquées dans le package, modifiables uniquement par release. **Reco** : le gouverner comme les tags — un artefact vivant éditable par les stewards (même workflow request/approve), versionné, par domaine. À terme il converge avec l'ontologie (K3) ; à court terme c'est le levier d'expansion le moins cher.

### K5 — Rien ne mesure la vie des documents (S2)

Aucun signal d'usage par doc : jamais cité, toujours cité, scores de similarité en baisse, âge. Fabrice a explicitement demandé la revalidation sur source modifiée + flag « Always Approve » (2026-05-26). **Reco** : compteurs d'usage par document alimentés par les traces (K1) — `citations_count`, `last_retrieved_at` — et une file de revalidation steward (docs jamais utilisés depuis N mois, docs très utilisés non revus). La détection de contradictions entre docs reste une décision produit **V2 stockée** (2026-05-22) — hors scope ici, on n'en propose pas la relance.

### K6 — Les réponses récurrentes ne cristallisent jamais (S3)

Les mêmes questions re-consomment le pipeline complet à chaque fois, et la connaissance synthétisée (souvent bonne) s'évapore. L'épisode FAQ retrieval-metrics (2026-07-03, question Romuald → FAQ rédigée à la main) est exactement ce pattern fait manuellement. **Reco** : **distillation FAQ** — clusteriser les questions récurrentes depuis les traces (K1), générer des brouillons d'articles KB sourcés, les faire valider steward, les ingérer comme documents de première classe (citables, taggés, folderisés). La KB se densifie là où on l'interroge.

### K7 — Synthèse de l'axe : la hiérarchie des dépendances

```
K1 (traces + feedback persistés)  ←  préalable unique
 ├── K2 gap ledger
 ├── K3 ontologie nourrie par l'usage (+ fix properties)
 ├── K5 signaux de vie des docs → revalidation
 └── K6 distillation FAQ
K4 thesaurus gouverné  ←  indépendant, quick win
```

Tout l'axe 2 tient sur **une** fondation : persister ce qui se passe. C'est peu de code (des writes Memgraph workspace-scopés, idiomes existants) et c'est ce qui transforme une KB interrogeable en capital qui se compose.

## Axe 3 — Features frontier

### F1 — Le Curateur nocturne (flagship recommandé)

Un agent batch qui tourne la nuit sur les L40S (lane batch) et produit chaque matin une **file de propositions** dans les workflows d'approbation existants :

- **tags rétroactifs** (docs anciens sous-taggés vs taxonomie courante) → tags governance ;
- **fusions d'entités du KG** (synonymes flous, entités trop génériques — le « graph cleaner », absent du code aujourd'hui : dédup nom-exact seulement, fuzzy = TODO `pipeline.py:206-209`) → dry-run/approve, même mécanique que DSEP ;
- **docs à revalider** (K5) et **gaps** (K2) → notifications steward ;
- **FAQ candidates** (K6) → review queue.

Pourquoi c'est la bonne frontier pour BNP : (a) **zéro nouvelle surface de risque** — tout passe par la validation humaine et l'audit trail déjà livrés, rien ne s'auto-applique ; (b) **profil de charge parfait** pour des GPU R&D (batch nocturne, corpus entier, D+2 appels par run DSEP — injouable sur un LLMaaS partagé) ; (c) **narrative produit** : la KB passe de « système qu'on interroge » à « système qui s'entretient et signale sa propre dette ». Pilote : 1 folder, 4 types de propositions, mesure du taux d'acceptation steward comme métrique de qualité du curateur.

### F2 — Mémoire organisationnelle multimodale

Gemma 4 31B est multimodal (texte+image) et validé groupe. Dans une KB IT ops, une part réelle de la connaissance vit dans des captures d'écran, schémas d'architecture, tableaux scannés — aujourd'hui invisibles à la retrieval. Pipeline R&D : vision → description structurée + texte extrait → chunks/vecteurs standards (le dérivé persisté est du texte : compatible doctrine « chunks+vecteurs », mais la persistance de dérivés LLM reste la décision compliance à cadrer, cf. décisions PO). Les schémas deviennent **citables** dans les réponses. Différenciant, démontrable en démo, et strictement additif au pipeline d'ingestion existant.

### F3 (mention, non retenue) — Retrieval auto-ajustante

Boucle bandit sur les paramètres de retrieval (top_k, seuils, mode) pilotée par le feedback. Moins mûre : dépend de K1 + du Retrieval Quality Lab + d'un volume de feedback qui n'existe pas encore. À réévaluer après 3 mois de traces.
