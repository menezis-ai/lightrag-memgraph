| Champ | Valeur |

| Branche | `feat/maquette-source-revalidation` (parent : `stable/0.6.x`) |

Objectif : valider la cohérence interne du L3 (schémas Pydantic, contrats inter-features, tests, patterns LLM, alignement DSEP, usage du routing F06) **avant** branchement via `_patch_intelligence_layer()`.

---

## TL;DR

Le L3 est une **façade fonctionnelle mais incomplète**. Les sous-systèmes existent, sont testés unitairement (env. 117 tests, 100 % offline), et le pipeline `aquery()` est démontré end-to-end avec LLM mocké. Les défauts structurants sont :

1. **`WorkspaceRouter` (F06) est code mort dans `aquery()`** : il existe, est testé (16 tests), publiquement importable, mais `TwinRAGEngine.aquery()` ne l'appelle nulle part. Le flag `enable_workspace_routing` ne fait rien. Le `routing_rules.json` n'est jamais chargé en production.
2. **`indexing_*` config est code mort** : la séparation chat/indexation est déclarée dans `TwinRAGConfig` mais aucun call site ne lit `indexing_api_key` / `indexing_api_base` / `indexing_model`. Tous les appels LLM utilisent `llm_api_key`/`llm_api_base`/`llm_model`.
3. **`AsyncOpenAI` est ré-instancié à chaque appel LLM** (7 call sites), confirmant le pattern anti-perf déjà flaggé par Prisme F §9. Aucune réutilisation de client / aucun pool.
4. **Le pipeline ACT ne parse pas correctement la sortie de `LightRAG.aquery()`** : en mode `hybrid`, LightRAG retourne une **string** (synthèse), pas une `list[chunk]`. `act.py:_parse_lightrag_result` traite la string comme un unique chunk de score 1.0 — donc la fusion multi-workspace et le rerank F04 travaillent sur des chunks dégradés (1 par workspace), pas sur des passages réels. Le `ChunkResult.document_path` est toujours `None` côté LightRAG, donc les citations OBSERVE ont un `document_path=None`.
5. **3 prompts non-utilisés** : `prompts/domain_system.txt` et `prompts/ontology_validate.txt` ne sont jamais chargés. Le step `VALIDATE` est purement Python, pas d'appel LLM, donc `ontology_validate.txt` est mort.
6. **Pas de test "anomaly injection"** au sens directive §3 : aucun test ne couvre JSON malformé, `{}` vide, timeout LLM, prompt injection dans la query (`<system>…</system>`), `RateLimitError`. Le seul "fallback" testé est `Exception` générique levée à l'instanciation `AsyncOpenAI`.
7. **`QueryTrace` n'a pas d'ID stable** — `FeedbackEntry.query_trace_id` est un `str` arbitraire fourni par l'appelant. Pas de génération auto, pas de UUID. Risque de collision en prod.
8. **Hooks LLM dispersés** : `temperature`, `seed`, `top_p` ne sont **pas** passés (donc défauts SDK). Pas de retry. Pas de gestion `RateLimitError`/`APITimeoutError`/`BadRequestError` spécifique — tout est `except Exception`.

Aucun secret en dur. Aucun TODO/FIXME dans le périmètre sauf un (`pipeline.py:215`, fuzzy match).

### 2.3 Bug latent : ESCALATION

`engine.py:118-147` traite `OOS`, `GREETING`, `MALICIOUS` mais **pas** `ESCALATION`. `_scripted_response(IntentType.ESCALATION)` est défini (`engine.py:216-219`) mais jamais appelé depuis `aquery`. Un user qui dit "incident P1, donne-moi un humain" passera donc dans le pipeline RAG complet plutôt que recevoir la réponse scriptée. C'est testé pour `test_scripted_response_escalation` (`test_engine.py:154-156`) qui teste seulement la fonction privée, pas l'integration.

### 2.4 Bug latent : ACT ne parse pas vraiment des chunks

`react/act.py:51-75` appelle `rag.aquery(query, param=QueryParam(mode="hybrid", top_k=20))`. Le contrat LightRAG en mode `hybrid` retourne **`str`** (la synthèse). `act.py:85-93` traite cette string comme un unique `ChunkResult` de score 1.0 et chunk_id `{workspace}_synthesis`.

Conséquence :
- `fuse_and_dedup` produit `len(all_workspaces)` chunks au total (un par workspace), tous de score 1.0.
- `cognitive_reranker.rerank` reçoit ≤ N_workspaces chunks et appelle 1 LLM call sur eux (au lieu de 10-20 chunks comme prévu) — le rerank devient quasi inutile.
- `observe.synthesize` reçoit une liste très courte de "passages" qui sont en fait des **résumés déjà synthétisés**. Le prompt OBSERVE demande de "citer des passages" mais ces passages sont eux-mêmes des réponses LLM. Stack overflow conceptuel.
- `Citation.document_path` est toujours `None` (jamais set côté `_parse_lightrag_result`), donc les citations cliquables WebUI n'ont rien à pointer.

Pour récupérer les vrais chunks de LightRAG sans synthèse, il faudrait `QueryParam(mode="hybrid", only_need_context=True)` (cf. Prisme F §3 et §4 — la stratégie A monkey-patch `LightRAG.aquery` mais aurait dû récupérer le param `only_need_context`). **Non corrigé**.

### 2.5 Workspaces et `_get_rag`

`engine.py:63-79` : crée un `LightRAG` par workspace, en exportant `os.environ["MEMGRAPH_WORKSPACE"] = workspace` **mutating global env** avant la construction. Effet : si deux `aquery()` concurrents sont sur des workspaces différents, la lecture de `MEMGRAPH_WORKSPACE` dans le pool peut renvoyer la mauvaise valeur. Race condition.

`act.py:83` lit `getattr(rag, "_workspace", "unknown")` — l'attribut `_workspace` n'est pas un attribut documenté de `LightRAG` (LightRAG n'a pas de `self._workspace`). Toujours `"unknown"`.

### 2.6 ESCALATION n'est pas l'unique cas oublié

`oos_confidence_threshold = 0.85` (`config.py:59`). Si Intent retourne `OUT_OF_SCOPE` avec `confidence < 0.85`, on **continue dans le pipeline** (`engine.py:120`) — c'est documenté comme "laisser passer". OK.

## 4. Intent classifier (F05)

### 4.1 IntentType

5 valeurs : `IN_SCOPE`, `OUT_OF_SCOPE`, `GREETING`, `MALICIOUS`, `ESCALATION` (`models/schemas.py:14-19`).

Manque : `LOW_CONFIDENCE` ou `UNKNOWN` distinct du fallback `IN_SCOPE confidence=0.0` — actuellement le fallback "erreur LLM" et "LLM dit IN_SCOPE confiance 0.0" sont indistinguables.

### 4.2 Prompt

- Source : `prompts/intent_system.txt` (25 lignes) — utilisé via `_load_system_prompt()` (`intent_classifier.py:25-28`).
- Fallback : `_DEFAULT_PROMPT` hardcodé (intent_classifier.py:31-59).

## 7. ReAct loop

### 7.1 REASON (`react/reason.py`)

- LLM call : OUI (`reason.py:120-134`), effort = `medium`, max_tokens=300.
- Inputs : `question`, `conversation_history` (truncated to `conversation_memory_depth=10`).
- Output : `ReasoningResult(thought, search_query, domain_hint, coreference_resolved, original_question)`.
- Fonctions : coreference resolution, technical domain detection, search query optimization.
- Fallback : `ReasoningResult(search_query=question)` sur exception.

### 7.2 ACT (`react/act.py`)

Pas de classe `Acting`. Une classe `SearchEngine` avec deux méthodes :
- `hybrid_search(rag, query, config)` : appelle `rag.aquery(query, param=QueryParam(mode="hybrid", top_k=20))`, parse le résultat.
- `fuse_and_dedup(workspace_results, workspace_names)` : dedup par `chunk_id`, sort par score.

**Multi-workspace** : oui, en `asyncio.gather(*[search.hybrid_search(rag_ws, ...) for ws in all_workspaces], return_exceptions=True)` (`engine.py:166-170`). Une workspace qui throw n'arrête pas les autres (return_exceptions=True), elle est juste loggée et ignorée (`act.py:126-128`).

**Anomalie** : voir §2.4 — `_parse_lightrag_result` ne récupère pas de vrais chunks.

### 7.3 OBSERVE (`react/observe.py`)

- LLM call : OUI (`observe.py:137-145`), effort = `high`, max_tokens=2048.
- Pas de `response_format={"type": "json_object"}` — la sortie est du texte libre (la réponse contient `[Passage X]` tokens).
- Extraction citations : regex `\[Passage (\d+)\]` (`observe.py:184`).
- Dedupe : oui (`observe.py:185`).
- Cleanup : la réponse retournée supprime les `[Passage X]` (`observe.py:151`).
- Citations construites depuis `Citation(passage_index, text=chunk.text[:500], document_id, document_path, source_workspace, score=chunk.rerank_score or chunk.score)`.

### 7.4 Boucle ReAct multi-step

Non. Le pipeline est **single-pass**. Pas de boucle Reason → Act → Observe → Reason → Act → ... Ce qui est nommé "ReAct" ici est en fait une pipeline statique 3-étapes. Pour vraie itération, il faudrait :
- détecter "insufficient context" dans OBSERVE,
- relancer REASON avec une query reformulée,
- éventuellement re-rerank ou élargir workspaces.

Pas de mécanisme. À noter pour roadmap.

**7 instanciations différentes à chaque appel**. Pas de réutilisation, pas de pool. C'est précisément l'anti-pattern flaggé par Prisme F §9.

Coût concret : la création d'un `AsyncOpenAI` (Python) est ~5-10 ms (parsing TLS, headers, etc.). Pour 4 calls/query, c'est ~30 ms overhead pur sur chaque requête.

### 12.2 `response_format={"type": "json_object"}`

| Module | response_format ? |
|---|---|
| intent_classifier | OUI (`:94`) |
| cognitive_reranker | OUI (`:104`) |
| reason | OUI (`:131`) |
| observe | **NON** (sortie texte libre) |
| ontology/extract | OUI (`:217`) |
| ontology/cluster | OUI (`:105`) |
| ontology/enrich | OUI (`:133`) |

OBSERVE n'utilise pas le JSON mode parce que la réponse contient les `[Passage X]` markers — c'est cohérent.

### 12.3 `temperature`, `top_p`, `seed`

**Aucun** call site ne configure `temperature` (donc 1.0 par défaut SDK), ni `top_p`, ni `seed`. Conséquence : pour les tâches déterministes (intent classification, reranking score), le LLM peut donner des réponses différentes au même prompt. Pour `gpt-oss-120b` self-hosted, c'est moins critique (on peut piloter au déploiement) — mais c'est un point de variance non-maîtrisée.

### 12.4 Retry / backoff

**Aucun**. Pas de `tenacity`, pas de `@retry`, pas de `for attempt in range(N)`.

Conséquence : un blip réseau ou un 503 transient = full fallback (intent → IN_SCOPE conf=0.0, reranker → top-K raw, OBSERVE → "Erreur lors de la synthese"). Pour OBSERVE c'est très visible utilisateur final.

### 12.5 Gestion erreurs spécifiques

Toutes les call sites font `except Exception`. Pas de gestion typée :
- `openai.RateLimitError` → devrait backoff exponentiel.
- `openai.APITimeoutError` → devrait retry court.
- `openai.BadRequestError` → ne sert à rien de retry (prompt trop long, bad model).

Ces classes existent dans le SDK openai-python 1.x.

Avec `gpt-oss-120b` self-hosted (BNP infra) :
- effort=low (~500 ms) × 2 (intent + rerank)
- effort=medium (~1500 ms) × 1 (reason)
- effort=high (~5000 ms) × 1 (synthesis)
- LightRAG.aquery × N_workspaces (~3000 ms en mode hybrid)

Sans paralléliser : ~10 000 ms + 3000 × N_workspaces.
Avec gather sur workspaces (ce qui est fait `engine.py:170`) : ~13 000 ms pour 2 workspaces.

Hypothèse : objectif < 5 s = pas atteint. À objectiver dès qu'on aura le branchement réel.

### 13.4 Coût

`gpt-oss-120b` self-hosted, donc coût = GPU-heure, pas tokens. Pas de chiffrage tokens utile en interne BNP.

### 13.5 Optimisations possibles

- **Cache LRU intent** (cf. §4.4) : -30 % coût F05 en pratique.
- **Reuse AsyncOpenAI client** (singleton via `lru_cache` ou module-level) : -30 ms / query overhead.
- **Fusion F05 + REASON** dans un seul LLM call ("classify and reformulate") : -1 call entier.
- **Rerank streaming** : retourner les chunks au fur et à mesure qu'ils sont scorés.
- **Pré-filtrage embedding** avant LLM rerank : si chunk cosine < seuil, skip rerank.

## Conclusion exécutive

Le L3 (`src/twindb_lightrag_memgraph/intelligence/`) est un overlay propre architecturalement, modulaire, unit-testé à ~117 tests offline. Mais il porte trois familles de problèmes :

1. **Code mort** : F06 router non branché, `indexing_*` config inutilisée, 4 feature flags sans effet, 2 prompts jamais chargés, 1 step VALIDATE qui contredit son prompt. Soit ~17/35 champs config morts.

2. **Bugs d'intégration** : ACT ne récupère pas de vrais chunks de LightRAG (cause = mode hybrid str-return), ESCALATION non early-exit, race condition env var workspace, citations sans `document_path`.

3. **Manque de tests d'effondrement** (directive §3) : aucun test JSON malformé, timeout, RateLimit, BadRequest, prompt injection sur passages.

Le code est mergeable mais le **branchement effectif sur LightRAG via `_patch_intelligence_layer()` doit attendre** la résolution des risques #1, #3, #4, #11 au minimum. Compter ~5-7 jours de fix.

Bonnes pratiques observées : pas de secret en dur, JSON partout, DSEP/deep_extraction nommage respecté, prompts `{{` `}}` escapés où nécessaire, mock import-path-exact dans les tests.
