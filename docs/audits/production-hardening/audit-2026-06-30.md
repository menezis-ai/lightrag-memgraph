### PH-001 — Overlay auth must fail closed in production

- **Severity:** Critical
- **Title:** Overlay authentication can remain permissive when production auth is misconfigured.
- **Affected files:** `src/twindb_lightrag_memgraph/server/app.py`, `src/twindb_lightrag_memgraph/server/auth.py`, `src/twindb_lightrag_memgraph/server/settings.py`, `src/twindb_lightrag_memgraph/patches/registry.py`, `ENV_VARIABLES.txt`, `README.md`
- **Description:** The Twin overlay has several auth modes: static API key, local JWT, and optional IdP middleware. Production deployment needs a fail-closed guard that refuses startup or refuses protected routes when no acceptable production auth backend is configured. The documented native LightRAG posture includes open/guest paths and local defaults; the overlay must make its own stricter production decision.
- **Production impact:** A mis-set environment variable can expose `/twin/api/*`, native shims, or mutating routes to unauthenticated users, especially behind a reverse proxy that assumes the app enforces auth.
- **Recommended remediation:** Add an explicit production auth policy, for example `TWIN_AUTH_MODE=strict`, that requires either validated IdP config or another approved enterprise mechanism. Fail startup with a clear error when strict mode lacks required settings. Keep local/demo defaults available only behind an explicit non-production flag.
- **Suggested tests:** Unit tests for strict startup failure with no auth; strict success with IdP config; strict rejection of local default credentials; integration tests proving `/twin/api/*`, native shim routes, and mutating routes return 401/403 when auth is absent.
- **Status:** Open

### PH-002 — RBAC is incomplete for mutating operations

- **Severity:** Critical
- **Title:** Folder, tag, graph, quota, and document mutations need route-level RBAC.
- **Affected files:** `src/twindb_lightrag_memgraph/server/idp_jwt.py`, `src/twindb_lightrag_memgraph/server/folder_store.py`, `src/twindb_lightrag_memgraph/server/webui/routes_folders.py`, `src/twindb_lightrag_memgraph/server/webui/routes_tags.py`, `src/twindb_lightrag_memgraph/server/webui/routes_graph.py`, `src/twindb_lightrag_memgraph/server/webui/routes_documents.py`, `src/twindb_lightrag_memgraph/server/quota_routes.py`
- **Description:** Admin gating exists conceptually through IdP groups/scopes, but the mutation surface is broader than folder administration. Route handlers that create, update, delete, approve, reject, deprecate, retag, patch graph objects, or change quotas need a consistent authorization matrix.
- **Production impact:** A user with read access to the knowledge base could alter taxonomy, graph facts, folder catalog entries, document metadata, or quotas if a route is protected only by authentication and not by role/scope.
- **Recommended remediation:** Define a small RBAC matrix (`read`, `ingest`, `tag_admin`, `folder_admin`, `graph_admin`, `quota_admin`) and enforce it through shared dependencies. Keep the claim mapping in `idp_jwt.py` and route dependencies declarative.
- **Suggested tests:** Parametrized route tests for each mutating endpoint with no scope, read-only scope, and the required admin scope. Include negative tests for cross-folder mutation attempts.
- **Status:** Open

### PH-003 — IdP issuer and audience validation need hard guarantees

- **Severity:** Critical
- **Title:** IdP JWT validation must require issuer and audience in production.
- **Affected files:** `src/twindb_lightrag_memgraph/server/idp_jwt.py`, `src/twindb_lightrag_memgraph/server/settings.py`, `ENV_VARIABLES.txt`, `tests/test_server/`
- **Description:** The IdP middleware supports mapped claims, JWKS, issuer, and audience variables, but production posture must make `iss` and `aud` validation mandatory when IdP auth is enabled. Optional issuer/audience creates a class of accepted tokens from the wrong tenant, client, or environment.
- **Production impact:** Tokens minted for another application, test tenant, or compromised adjacent audience may be accepted by Twin.
- **Recommended remediation:** In strict/production auth mode, require `TWIN_IDP_ISSUER` and `TWIN_IDP_AUDIENCE`; reject tokens missing matching `iss` and `aud`; document the expected BNP values in deployment-specific runbooks without committing secrets.
- **Suggested tests:** JWT validation tests for wrong issuer, missing issuer, wrong audience, list-valued audience, expired token, wrong `kid`, and happy path.
- **Status:** Open

### PH-004 — MIP PDF/OLE parsing dependencies can fail open

- **Severity:** High
- **Title:** Missing optional MIP parsers can downgrade classification enforcement.
- **Affected files:** `src/twindb_lightrag_memgraph/classification.py`, `src/twindb_lightrag_memgraph/_classification_hook.py`, `pyproject.toml`, `requirements/`, `README.md`, `docs/operations/install-runbook.md`
- **Description:** MIP extraction for PDF and legacy Office formats depends on optional packages such as `pikepdf` and `olefile`. If they are absent, detection can return `UNKNOWN`/missing metadata rather than a hard rejection, depending on policy.
- **Production impact:** Classified PDF/OLE documents may be ingested when the runtime image lacks the parser needed to detect their label.
- **Recommended remediation:** Add a production policy for parser absence. For BNP strict classification, fail closed for file types whose configured classifier dependency is unavailable, or remove those extensions from accepted upload types. Include dependency presence in image smoke checks.
- **Suggested tests:** Tests simulating missing `pikepdf`/`olefile` for labelled and unlabelled files; strict mode rejection; non-strict mode graceful degradation with explicit audit event.
- **Status:** Open

### PH-005 — MIP rejection summaries may leak sensitive metadata

- **Severity:** High
- **Title:** Classification rejection responses and audit events must not expose sensitive document details.
- **Affected files:** `src/twindb_lightrag_memgraph/_classification_hook.py`, `src/twindb_lightrag_memgraph/classification.py`, `src/twindb_lightrag_memgraph/server/webui/events.py`, `src/twindb_lightrag_memgraph/server/webui_activitystore.py`
- **Description:** Rejection paths need to record enough information for operators without echoing labels, document names, summaries, extracted text, or metadata that could reveal sensitive content to unauthorized users.
- **Production impact:** A user who attempts or observes a rejected upload may learn the existence, filename, sensitivity class, or business context of a restricted document.
- **Recommended remediation:** Redact rejection payloads by default. Store only document hash/track id, coarse class comparison result, actor, folder, and reason code. Gate detailed diagnostics behind admin-only logs.
- **Suggested tests:** Rejection tests asserting no original filename, content summary, extracted label GUID, or text fragment appears in HTTP response, notification, or user-visible activity event.
- **Status:** Open

### PH-006 — Classification metadata persistence errors can be swallowed

- **Severity:** High
- **Title:** Classification metadata writes need observable failure semantics.
- **Affected files:** `src/twindb_lightrag_memgraph/_classification_hook.py`, `src/twindb_lightrag_memgraph/docstatus_impl.py`, `src/twindb_lightrag_memgraph/server/webui/routes_documents.py`, `tests/test_classification_hook.py`
- **Description:** The classification hook should not silently lose metadata when DocStatus updates fail or when LightRAG later overwrites metadata during processing. Classification is part of the compliance decision, not best-effort decoration.
- **Production impact:** Documents can appear processed without a reliable persisted classification trail, making downstream access decisions and audit reconstruction weaker.
- **Recommended remediation:** Make metadata persistence idempotent and verifiable. Emit a structured audit event on persistence failure, preserve existing classification keys across DocStatus transitions, and consider failing ingestion if strict classification metadata cannot be stored.
- **Suggested tests:** Simulate DocStatus write failure; verify audit event; verify classification metadata survives PENDING -> PROCESSING -> PROCESSED transitions and duplicate/retry paths.
- **Status:** Open

### PH-008 — Production entrypoints lack enough regression coverage

- **Description:** The production doctrine depends on `register()` running before LightRAG server import. The three launch surfaces have different activation rules and should be guarded against import-order regressions.

- **Suggested tests:** Monkeypatch import sentinels for `twin_main.py`, `python -m twindb_lightrag_memgraph.lightrag_server`, and `asgi:get_application()`. Add a subprocess smoke for the module entrypoint if feasible.

### PH-012 — SSO logout semantics need verification

- **Severity:** Medium
- **Title:** Logout must clear local session state and align with IdP expectations.
- **Affected files:** `src/twindb_lightrag_memgraph/server/auth.py`, `src/twindb_lightrag_memgraph/server/idp_jwt.py`, `src/twindb_lightrag_memgraph/server/native_shims.py`, `lightrag_webui_twin/src/hooks/useAuth.ts`, `lightrag_webui_twin/src/api/client.ts`
- **Description:** Local logout clears local cookies/tokens, but enterprise SSO logout may also require redirect, front-channel logout, or at least avoiding a misleading “signed out” state while the IdP cookie immediately reauthenticates the user.
- **Production impact:** Users may remain authenticated after logout or be silently reauthenticated, creating confusion for shared workstations and audit trails.
- **Recommended remediation:** Define BNP logout semantics: local-only clear, IdP redirect, or reverse-proxy-controlled logout. Implement one behavior consistently across native shim and WebUI.
- **Suggested tests:** Browser/e2e test for logout clearing `twin_local_token`, auth status after logout, and IdP-enabled logout response shape. Add native `/logout` shim coverage.
- **Status:** Watch/verify

### PH-013 — Streaming unauthorized responses need end-to-end verification

- **Severity:** High
- **Title:** Streaming query routes must reject unauthorized clients before opening a stream.
- **Affected files:** `src/twindb_lightrag_memgraph/server/query/router.py`, `src/twindb_lightrag_memgraph/server/native_shims.py`, `src/twindb_lightrag_memgraph/server/auth.py`, `lightrag_webui_twin/src/api/client.ts`, `tests/test_server/`
- **Description:** Streaming endpoints can accidentally return `200` and then emit an auth error inside the stream if auth checks happen too late or exceptions are swallowed by the streaming generator.
- **Production impact:** Proxies, browsers, and audit logs can record unauthorized streaming requests as successful, and clients may expose confusing partial results.
- **Recommended remediation:** Resolve auth and folder binding before constructing `StreamingResponse`. Ensure exceptions become normal HTTP 401/403 responses before headers are sent.
- **Suggested tests:** Unauthenticated streaming request returns 401 with no stream body; invalid folder returns 400/403 before stream start; WebUI client handles 401 by forcing auth refresh.
- **Status:** Watch/verify

### PH-014 — Folder selector can imply authorization beyond its scope

- **Severity:** Medium
- **Title:** UI folder selection is not a substitute for server-side folder authorization.

### PH-015 — Graph batch mutations are not atomic

- **Severity:** High
- **Title:** Batched graph writes can partially apply without transaction-level rollback.
- **Affected files:** `src/twindb_lightrag_memgraph/server/graph_reader.py`, `src/twindb_lightrag_memgraph/server/webui/routes_graph.py`, `src/twindb_lightrag_memgraph/_buffered_graph.py`, `tests/test_server/`
- **Description:** Graph create/patch/delete helpers and buffered graph writes may execute multiple Cypher statements. If one statement fails, earlier statements may already be committed unless wrapped in a single transaction.
- **Production impact:** Operators can leave entity/relation state inconsistent, with graph UI and retrieval observing partial facts.
- **Recommended remediation:** Wrap each logical batch mutation in one explicit Memgraph transaction. Return an all-or-nothing result and include conflict details for validation errors before writes.
- **Suggested tests:** Inject failure after first statement and assert no graph changes persist; concurrent mutation conflict test; batch delete/create rollback tests.
- **Status:** Open

### PH-019 — Prompt injection can cross reasoning steps
