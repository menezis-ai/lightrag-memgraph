# Audit ingestion / reindex — 2026-07-02

Audit croisé en 5 axes : pipeline upload→parse→chunk→embed→graph (transitions de
statut, pannes partielles, retries, invariants UI), isolation compat LightRAG,
sûreté des écritures Memgraph, couverture CI réelle des chemins
ingestion/reindex, duplication inter-surfaces. Lecture seule ; aucun fichier de
code modifié.

**Méthode.** Cinq passes indépendantes (une par axe), puis contre-vérification
en thread principal des findings de tête sur le **wheel PyPI exact
`lightrag-hku==1.4.9.11`** extrait en scratchpad — pas sur le `.venv`.
Chaque finding porte CONFIRMED (chemin lu de bout en bout, file:line) ou
INFERRED (plausible, avec ce qui le confirmerait). Le prochain volet prévu est
l'audit query/retrieval grounding (hors scope ici).

**Antériorité — ne pas re-dériver :**
- `docs/audits/lightrag-1.4.9.11/prisme-H-ingestion-pipeline.md` reste
  l'autorité sur la trace upstream 1.4.9.11 : machine à états (§1.2), absence
  de transaction Memgraph globale (§5.2), races entités partagées (§5.3),
  crash à mi-chemin (§6.2), `reprocess_failed` (§6.3).
- `docs/audits/production-hardening/audit-2026-06-30.md` tracke déjà PH-006
  (erreurs de persistance classification avalées), PH-015 (mutations graph
  batch non atomiques), PH-017 (bornes pagination DocStatus). Les
  recoupements ci-dessous pointent vers ces IDs au lieu de les dupliquer.

## Baseline versions — un skew au-delà de la matrice documentée

Le `.venv` local porte **lightrag-hku 1.5.4** (confirmé via
`importlib.metadata` ; pas de pip dans le venv). C'est **hors matrice CI**
(1.4.9.11 / 1.4.11 / 1.4.12, `.forgejo/workflows/ci.yml:44,91`) — plus large
que le skew déjà mémorisé (`feedback_lightrag_version_skew`). Conséquence
concrète : en 1.5.4 le process loop a déménagé de `lightrag/lightrag.py` vers
`lightrag/pipeline.py` et la machine à états s'est élargie
(`PENDING → PARSING → ANALYZING → PROCESSING → PROCESSED|FAILED`,
`base.py:793-805`) — deux patchs du repo changent de comportement silencieusement
en local (voir SKEW-1, SKEW-2). Toute référence `lightrag/...` ci-dessous
précise sa version.

## Findings S1

### ING-1 — Le gate de classification MIP ne protège PAS la surface d'ingestion principale (pin BNP 1.4.9.11) — CONFIRMED

Chaîne complète, contre-vérifiée en thread principal sur le wheel 1.4.9.11 :

1. Les routes natives d'ingestion 1.4.9.11 (`POST /documents/upload`,
   `/documents/text`, `/documents/texts`, `/documents/scan`) appellent
   `rag.apipeline_enqueue_documents` + `rag.apipeline_process_enqueue_documents`
   (`document_routes.py:1563,1661,1696,1724,1727,…`). **Zéro occurrence de
   `rag.ainsert`** dans tout `document_routes.py` (grep exhaustif du wheel).
2. Le hook MIP ne patche que `LightRAG.ainsert`
   (`_classification_hook.py:504-506`) ; il n'existe **aucun** patch du chemin
   enqueue (grep `enqueue|pipeline_index` = 0 hit dans `_classification_hook.py`,
   0 patch `apipeline` dans `patches/registry.py`). L'unique site d'invocation
   du hook est `_classification_hook.py:418`, dans `_patched_ainsert`.
3. `native_shims.py` ne définit aucune route upload (grep = 0) — l'upload WebUI
   atterrit sur la route native LightRAG.
4. Le header `X-Twin-Classification` envoyé par l'UI est bien bindé par le
   middleware (`patches/registry.py:1648-1656` →
   `operator_classification_context`), mais l'unique consommateur de cette
   ContextVar (`get_active_operator_classification`) vit dans le hook ainsert
   qui ne s'exécute jamais sur ce chemin (`_classification_hook.py:48,142` ;
   `registry.py:1540-1547` ne fait que propager le contexte à travers
   BackgroundTasks).
5. Seule la route overlay `POST /insert` est gardée (`server/app.py:992` →
   `rag.ainsert`).

**Scénario** : `classify=True` activé, un opérateur uploade un document C4 via
la WebUI → indexation complète, plafond `TWIN_MIP_MAX_CLASSIFICATION` jamais
évalué, aucun événement `classification-rejected`. Le header opérateur est
poliment transporté puis jeté.

**Pourquoi la CI est verte** : `tests/test_classification_gate.py` n'exerce le
gate que via `rag.ainsert(...)` directement (lignes 238-288) — le contrat
« la route HTTP d'upload passe par le gate » n'est testé nulle part. C'est le
cas d'école du faux-vert par test au mauvais niveau.

Part INFERRED : l'activation effective de `classify` dans l'env BNP (le défaut
est off). Le défaut de conception est confirmé indépendamment de ça : la
feature, telle que livrée, ne couvre pas sa surface primaire.

### ING-2 — La couverture « e2e-real » de l'ingestion est vacueuse, et la dédup re-upload n'a aucune couverture bout-en-bout sur le pin — CONFIRMED

Deux volets (agent tests, file:line vérifiés) :

- **(TEST-2)** Le job `webui-e2e-real` n'ingère **zéro octet** :
  `REAL_E2E_UPLOAD_FOR_DELETE: "false"` (`ci.yml:274`, commentaire explicite
  « native upload starts indexing and would hit the intentionally disabled
  OpenAI credentials »), la lib api-coverage n'a pas de route
  `/documents/upload` (`e2e/lib/api-coverage.ts:58-69`), et la cible du
  bulk-delete est seedée **sans chunks** par Cypher direct
  (`scripts/real_backend_e2e_fixtures.py:27-55`). Tout ce que « real » couvre
  en mutation = CRUD overlay sur des DocStatus synthétiques.
- **(TEST-1)** Le comportement protecteur de données « même fichier uploadé
  deux fois → membership ajoutée, pas de double ingestion » n'est testé
  bout-en-bout sur **aucune** version : unit = fonctions pures/sessions
  mockées ; intégration = appels directs aux hooks storage
  (`test_folder_membership.py:138-226`) sans jamais prouver que LightRAG les
  invoque ; et `test_upload_duplicate_lookup.py:48-52` **s'auto-skip sur
  1.4.9.11** — le pin prod. C'est exactement la classe de contrat qui varie
  par version (cf. incident 2026-06-24).

Positif à garder en tête (TEST-7) : la CI exerce bien DEUX vrais pipelines
d'ingestion contre Memgraph réel — `tests/test_e2e.py:281-367` (`ainsert`
complet, LLM mock déterministe au format extraction) et
`tests/test_native_document_runtime.py:224-260` (upload HTTP natif multipart →
poll PROCESSED → chunks/membership/Vec asserts, + `reprocess_failed`). Le
problème n'est pas « rien ne teste l'ingestion », c'est que tout le
version-sensible et le panne-sensible autour de ces deux fichiers est mocké,
skippé ou absent.

### Compat LightRAG (axe 2)

Réponse à la question posée (« isolé ou dispersé ? ») : **le monkeypatching est
bien centralisé** (12 sites de patch dans `patches/registry.py` + 1 seul
hors-registry : le patch `ainsert` de `_classification_hook.py:504-505`),
**mais la consommation d'API LightRAG est dispersée** : ~53 clusters de sites,
dont ~34 hors des deux modules dédiés (`registry.py`,
`server/_lightrag_compat.py`), répartis sur 15 fichiers. La majorité touche de
l'API publique stable ; les risques réels :

- **COMPAT-1/2 — La factory serveur standalone est cassée sur TOUTES les
  versions supportées — CONFIRMED.** `server/app.py:1186` importe
  `openai_embedding` (le nom upstream est `openai_embed` en 1.4.9.11 **et**
  1.5.4) et `app.py:602` appelle `_rag.initialize()` (seul
  `initialize_storages()` existe). Deux breaks indépendants sur le même
  chemin = ce lifespan n'a jamais tourné contre un vrai LightRAG — code
  non falsifié, les tests le mockent. À corriger ou supprimer ; aujourd'hui il
  suggère faussement un mode de déploiement non-overlay fonctionnel. (Pas S1 :
  BNP passe par `register()` sur le serveur LightRAG natif.)
- **COMPAT-3 — Copies privées de `operate._get_node_data` /
  `_find_most_related_edges_from_entities` : décrochage silencieux garanti à
  un bump — CONFIRMED (bénin aujourd'hui).** Corps upstream diffés : identiques
  1.4.9.11 ↔ 1.5.4, copies fidèles. Mais un rename upstream = le setattr ne
  crashe pas, le patch cesse juste d'être appelé (régression perf muette) ; un
  changement de corps = drift de qualité retrieval invisible aux tests. Aucune
  assertion de présence ni canari de checksum.
- **COMPAT-4 — Classe « crash au boot sur rename » : lectures nues de symboles
  upstream dans `register()` — CONFIRMED.** `operate.merge_nodes_and_edges`
  (`registry.py:1078`), `LightRAG._insert_done` (`:1111`, signature 2-args
  codée en dur), `create_document_routes` (`:1332`), `create_app` (`:1494`),
  les 3 dicts `lightrag.kg` (`:85-105`). Même classe que l'incident
  2026-06-24, sur des symboles qui existent encore — un rename et l'instance
  BNP ne sert plus rien.
- **COMPAT-5 — Guard hasattr à moitié — CONFIRMED.** Le fix post-incident
  guarde `find_existing_file_by_file_path` (`registry.py:1437`) mais le corps
  de remplacement consomme `dr.normalize_file_path` (`:1374`) et
  `dr.UNKNOWN_FILE_SOURCE` (`:1401`), tous deux absents de 1.4.9.11 et
  seulement co-guardés par heuristique.
- **COMPAT-6 — Le patch `ainsert` forwarde 6 args positionnels — CONFIRMED.**
  Signature identique 1.4.9.11/1.5.4 aujourd'hui ; une insertion de paramètre
  upstream = décalage silencieux (classe corruption, pas crash).
- **COMPAT-7 — Commentaire compat mensonger — CONFIRMED.**
  `_import_cleanup.py:20-33` : « LightRAG 1.4.9.11+ » sur `utils_pipeline`,
  qui **n'existe pas** dans le wheel 1.4.9.11 (il apparaît en 1.5.x). Le
  fallback fonctionne mais le commentaire est un piège d'audit.
- **SKEW-1 (ex-PIPE-2, requalifié) — Le patch buffered-merge est mort sur le
  1.5.4 local, vivant sur le pin — CONFIRMED des deux côtés.** En 1.4.9.11,

- **SKEW-2 (ex-PIPE-1 volet 1.5.x)** : même bascule pour le gate MIP — en
