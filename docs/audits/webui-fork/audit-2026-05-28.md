## Section 1 — Architecture globale

### 1.1 — Entry point & bootstrap

```
index.html (root #root)                                   index.html:10
   ↓
src/main.tsx::bootstrap()                                 src/main.tsx:6-18
   ↓ (DEV only)
import('./mocks/browser').then(startMsw)                  src/main.tsx:7-9, src/mocks/browser.ts:13-21
   ↓
createRoot(...).render(<StrictMode><App /></StrictMode>)  src/main.tsx:11-15
   ↓
App = QueryClientProvider(client) → AppShell             src/App.tsx:416-422
```

- `bootstrap` est `async`, encapsule `void bootstrap()` (`main.tsx:18`). MSW est dynamiquement importé (`await import('./mocks/browser')`, `main.tsx:8`) pour ne pas peser sur le bundle prod (tree-shake).
- Garde MSW : `import.meta.env.DEV && import.meta.env.VITE_USE_MSW !== 'false'` (`main.tsx:7`). En prod (`VITE_USE_MSW=false` ou non-DEV), le worker n'est jamais démarré → les fetches passent réellement à `BASE_URL`.
- `StrictMode` actif → double-mount des effects en dev. Aucune dérogation visible.

### 1.2 — App shell & routing

**Pas de router.** L'app est mono-page avec un state `tab: string` géré dans `AppShell` (`App.tsx:94`) et reflété en URL via `window.history.replaceState` dans `onNavigate` (`App.tsx:274-287`).

Les sous-tabs (Documents, Retrieval, Tags, Activity, Graph, API) sont conditionnellement montés en JSX :

```tsx
{tab === 'documents' && <DocumentsTab ... />}            App.tsx:329-338
{tab === 'retrieval' && <RetrievalTab ... />}            App.tsx:339-346
{tab === 'activity' && <ActivityTab ... />}              App.tsx:347-356
{tab === 'graph' && <GraphTab ... />}                    App.tsx:357-363
{tab === 'api' && <ApiTab ... />}                        App.tsx:364-371
{tab === 'tags' && <TagsTab ... />}                      App.tsx:372-381
```

L'effet visuel "tab transition" vient d'une re-key sur la div parente (`key={tab}` `App.tsx:328`), qui force un remount, animé via `.tab-pane` keyframes dans `legacy.css:1240-1248`. Conséquence : chaque switch de tab détruit le state interne de l'ancien tab (sélection multi-row de Documents, scroll de Retrieval, etc.). C'est intentionnel — la persistance live dans l'URL via `useUrlParam` (filtres) et dans `localStorage` (threads de Retrieval, position de TweaksPanel).

**Aucun deep-linking par path.** Tout passe par `?tab=` + `?<param>=` (cf. §2 et §5).

**Aucun code-splitting.** Tous les tabs sont importés en haut d'`App.tsx` (`App.tsx:23-32`), donc ils sont tous présents dans le bundle initial. Voir §11 pour les tailles concrètes — `dist/assets/index-DyRtwTdf.js = 366.5 KB` minified, `index-BT74h3ai.css = 96.4 KB`. C'est un seul chunk JS.

### 1.3 — Providers React

Un seul provider monté : `QueryClientProvider` (`App.tsx:418-420`). Le `QueryClient` est instancié au module-load (`App.tsx:84-91`) avec defaults `retry: 1, refetchOnWindowFocus: false`. Pas de provider de thème (le thème est appliqué via `document.documentElement.setAttribute('data-theme', theme)` `App.tsx:125-127`). Pas de provider d'auth. Pas de `ErrorBoundary` global. Pas de `Suspense` boundary (lazy-load absent).

## Section 2 — State management

### 2.1 — Inventaire des stores

Le fork **n'utilise ni Redux ni Zustand**. La doctrine est :

| Type de state | Outil | Localisation |
|---|---|---|
| State global UI (`tab`, `theme`, `workspace`, `toasts`, modals) | `useState` dans `AppShell` | `App.tsx:94-103` |
| State serveur (queries / mutations) | **TanStack Query v5** | `src/api/queries.ts:10-228` |
| State URL-backed (filtres, pagination, modes) | `useUrlParam` custom | `src/hooks/useUrlParam.ts` (3 variantes) |
| State persistant client | `localStorage` direct | `RetrievalTab.tsx:46, 77, 110`, `TweaksPanel.tsx:33, 41-62` |
| State par tab | `useState` interne au composant | partout |

**Zéro Context React.** TagsTab+TagActionModal communiquent via props/callbacks et `setModal` state (`TagsTab.tsx:67, 376-387`). Le `currentUser` est passé en prop depuis `App.tsx:78-82` (CURRENT_USER hardcodé pour la démo, `claire.benoit / palier 3`).

### 2.2 — Palier courant

Pas d'état runtime modifiable. Le `CURRENT_USER` est hardcodé en haut d'`App.tsx:78-82` avec `palier: 3, role: 'admin / steward'`. Passé en prop à `TagsTab.tsx:48-54`. Aucun PalierSwitcher dans le fork (contrairement à la maquette qui a un `?palier=N` URL switch `topbar.jsx:213-218`).

**Implication** : pour porter le palier-switching, il faudra ajouter soit un Context, soit lever ce state dans `AppShell`, soit l'ancrer en URL. La logique de gating est par contre déjà en place : `canEdit = currentUser.palier >= 3` (`TagsTab.tsx:101`), `canSuggest = currentUser.palier >= 2` (`TagsTab.tsx:102`). Le palier 4 "knowledge" (validé par Fabrice 2026-05-26) n'apparaît nulle part.

### 2.3 — Workspaces

State `workspace: string` dans `AppShell` (`App.tsx:96`), initialisé à `'cib'`. Mutation via `onSwitchWorkspace={(w) => setWorkspace(w.id)}` (`App.tsx:311`). La liste vient de `useWorkspaces()` (`App.tsx:107`) qui hit `/workspaces` (`resources.ts:37-38`). Fallback fixture `WORKSPACE_FIXTURES` (`App.tsx:130`).

**Le `workspace` n'est PAS répercuté sur les autres queries.** `useDocuments({status})` ne passe pas de `workspace` au backend (`queries.ts:16-22`), idem `useTags`, `useActivity`, `useGraphEntities`. Le filtrage workspace est implicite côté serveur (label `KV_{workspace}_*` selon l'archi Memgraph) — ce qui suppose que l'auth tranche pour l'utilisateur. Mais comme il n'y a pas d'auth runtime (cf. §12), changer de workspace ne change rien à ce que les queries renvoient en l'état.

**Conséquence pour la prod** : le contrat backend doit soit (a) accepter `?workspace=` sur toutes les routes listing, soit (b) re-tirer la connaissance depuis l'auth (claim JWT). En tout cas la `queryKey` doit inclure le workspace pour invalidation propre — actuellement `useDocuments` a `queryKey: ['documents', query]` (`queries.ts:18`), `useTags` a `['tags']` (`queries.ts:66`) → quand on changera de workspace, le cache TQ servira l'ancien workspace tant que pas invalidé.

### 2.4 — Notifications

Double-state intentionnel (`App.tsx:118-123`) :
- query `useNotifications()` (source of truth backend, `queries.ts:32-38`)
- `useState<Notification[]>(NOTIFICATION_FIXTURES)` côté client (mute mutable : `read`/`cleared`)

```tsx
const [notifications, setNotifications] = useState([...NOTIFICATION_FIXTURES]);
useEffect(() => {
  if (notificationsQ.data) setNotifications([...notificationsQ.data]);
}, [notificationsQ.data]);
```

L'idiome : refetch écrase le state local. **Bug latent** : si la refetch arrive après que l'utilisateur a marqué N notifications comme lues, les `read` flags locaux sont écrasés (perte d'état UI). Le commentaire `App.tsx:119` reconnaît : *"Notifications carry mutable client state (read/cleared) on top of the query data, so we mirror them locally"* mais ne résout pas le merge. En prod il faut soit (a) poster `read-all` au backend et invalider avant refetch, soit (b) merger les `read` flags localement.

Les hooks `useMarkAllNotificationsRead` et `useClearNotifications` existent (`queries.ts:40-54`) mais **ne sont jamais appelés** depuis `App.tsx` — `onMarkAllRead` (`App.tsx:315-317`) et `onClearNotifications` (`App.tsx:318`) mutent seulement le state local. **Wiring incomplet du Prisme C** : 2 routes définies, 2 routes mortes.

### 2.5 — Tags / thesaurus

- `useTags()` + `useTagCategories()` + `useThesaurus()` montés dans `AppShell` (`App.tsx:109-111`) → query keys `['tags']`, `['tag-categories']`, `['thesaurus']` (`queries.ts:65-78`).
- Mutations centralisées : `useRequestTag`, `useApproveTag`, `useRejectTag`, `useEditTag`, `useDeprecateTag`, `useUpdateTagSynonyms`, `useDeleteTag` (`queries.ts:130-220`).
- **Invalidation propre** : chaque mutation appelle `invalidateTagSideEffects(qc)` qui invalide `['tags']`, `['activity']`, `['notifications']` (`queries.ts:130-134`). C'est cohérent avec la doctrine documentée `project_webui_fork.md` : *"WebUI mutation hook → FastAPI endpoint → store Memgraph → cache invalidation → WebUI refetch"*.
- **Note** : `useRequestTag` n'a PAS d'argument workspace, le backend doit le résoudre de l'auth.

### 2.6 — Stale time & retry

Defaults globaux : `staleTime: 60_000` (`queries.ts:14`), `retry: 1, refetchOnWindowFocus: false` (`App.tsx:84-91`). Pas de `refetchInterval` sur les notifs (donc pas de polling natif — la maquette poll toutes les 9s `activity.jsx:246-249`, ici Activity tab a son propre `setInterval(... 9000)` `ActivityTab.tsx:81-85`).

### 2.7 — localStorage usages

| Clé | Composant | Comportement |
|---|---|---|
| `twin-rag.threads.v2` | RetrievalTab | Lecture initiale (`RetrievalTab.tsx:75-83`), persiste sur tout changement (`RetrievalTab.tsx:108-114`). |
| `twin-tweaks.position` | TweaksPanel | Position xy du panel flottant (`TweaksPanel.tsx:33, 41-62`). |

Pas d'autres clés. Pas de cache backend mirror. Pas de JWT/refresh-token persisté (le `AUTH_TOKEN` est lu du build-time env, `client.ts:16`).

### 2.8 — Routing state via URL

Les filtres de tab sont reflétés en URL via `useUrlParam` (`useUrlParam.ts:36-67`). Liste détaillée par tab :

| Tab | Params URL |
|---|---|
| Documents | `status`, `q`, `tag` (array) | `DocumentsTab.tsx:65-76` |
| Retrieval | `rtag` (array), `mode`, `topk`, `maxtok`, `hist` | `RetrievalTab.tsx:91-98` |
| Tags | `cat`, `status`, `q`, `tag` | `TagsTab.tsx:55-65` |
| Activity | `range`, `kind` (Set), `sev`, `q`, `actor` | `ActivityTab.tsx:58-73` |
| Graph | `gq`, `gtype` (array), `gent` | `GraphTab.tsx:45-53` |

Le pattern est cohérent partout : default-stripped (URL clean quand defaults), `validate` callback pour rejeter les valeurs invalides, parse/serialize personnalisables (Sets, arrays).

**Piège connu** (commenté dans le code, `useUrlParam.ts:62-64`) : *"We intentionally only depend on `val`. `key`/`defaultValue`/`serialize` are treated as stable per render — matching the proto's behavior."* avec `// eslint-disable-next-line react-hooks/exhaustive-deps`. Si un appelant change `defaultValue` après mount, l'URL n'est pas réécrite ; généralement OK puisque les defaults sont des littéraux mais à connaître.

**Pas d'autres hooks customs.** Les patterns `useDocuments`, `useTags`, etc. dans `queries.ts` sont des wrappers TanStack Query, pas des hooks "custom" au sens classique.

### Pièges connus (cf. `project_webui_fork.md`)

1. **`useModalA11y` 30ms autofocus piège** (`useModalA11y.ts:55`) : *"Defer to let layout settle (modal mount animation, etc.) → setTimeout(..., 30)"*. Si on type dans un input non-premier juste après ouverture, l'autofocus du hook peut voler la frappe. Mitigation dans les tests : `await new Promise((r) => setTimeout(r, 60))` puis `.focus()` explicite avant `userEvent.type` (voir `TagsTab.test.tsx:276-277` pour le Reject modal). 

2. **`userEvent.type(... 'foo{Enter}')` races sur CI Bun** (`project_webui_fork.md` memory). Le pattern correct : split en 2 appels + `waitFor`. **Statut** : appliqué dans `TagsTab.test.tsx:297-301` mais **violé** dans `RetrievalTab.test.tsx:185` (`await userEvent.type(input, 'oracle{Enter}')`). À surveiller en CI ; potentiel flake.

3. **ARIA live regions duplicate visible text** (`ToastViewport.tsx:62-68`). Les régions polite/assertive contiennent le texte du toast → un `getByText('Tag applied')` ramène 2 matches. Mitigation : scope avec `.toast-viewport` (`ToastViewport.test.tsx:60-66`). Documenté.

4. **`useUrlParam` exhaustive-deps bypass** (`useUrlParam.ts:63`) : `// eslint-disable-next-line react-hooks/exhaustive-deps`. Comportement intentionnel mais reste un trou de filet : si `serialize` n'est pas stable (closure), la persistance URL peut diverger silencieusement. Tous les usages actuels passent des fonctions inline mais que React mémoïse trivialement.

5. **`useEffect` dans RetagModal avec `targetsKey` string-key** (`RetagModal.tsx:91-99`). Recalculer un `join(',')` à chaque render pour disambiguer la dépendance est une astuce — fragile si un `id` contient une virgule. Les ids `d1, d2, d3` sont safe mais à connaitre.

## Section 12 — Compatibilité avec l'extension `register()`

### 12.1 — Configuration `BASE_URL` runtime

État actuel (`src/api/client.ts:15-16`) :

```typescript
const BASE_URL = (import.meta.env.VITE_API_BASE_URL ?? '').replace(/\/$/, '');
const AUTH_TOKEN = import.meta.env.VITE_AUTH_TOKEN ?? '';
```

**Problème** : `import.meta.env.VITE_*` est **résolu au build-time, pas au runtime**. Une fois le bundle livré, `BASE_URL` est figé. Pour un déploiement Twin où le même bundle sert plusieurs workspaces (multi-tenant) ou pour permettre à l'opérateur de pointer vers un staging vs prod, il faut :

**Option A** : Bake une URL relative (`VITE_API_BASE_URL=''` ou unset, donc same-origin), et laisser le reverse-proxy faire le routage. C'est la plus simple et la plus alignée avec l'extension `register()` qui sert le WebUI sous le même origin que l'API.

**Option B** : Injecter un `window.env` au boot, avant `main.tsx`. Pattern courant :
```html
<script src="/config.js"></script>  <!-- ré-écrit par nginx au déploiement -->
<script type="module" src="/src/main.tsx"></script>
```
puis modifier `client.ts:15` en `const BASE_URL = window.__TWIN_ENV__?.API_BASE_URL ?? '';`. Mais cela impose un cast et un `vite-env.d.ts` étendu.

**Option C** : Lire un `<meta name="twin-api-base">` du HTML. Moins propre.

**Recommandé pour `register()`** : Option A — same-origin + `register()` monte `/twin/static/*` pour les assets et `/twin/api/*` pour les endpoints. Le fork actuel attend `/documents`, `/tags`, etc. à la racine (pas de prefix). Il faudra soit :
- bake `VITE_API_BASE_URL=/twin/api` au build time → tous les fetches deviennent `/twin/api/documents`, etc.
- ou patcher `resources.ts` pour préfixer toutes les routes (lourd).

### 12.2 — Routes root-level vs préfixées

Les 19 routes dans `resources.ts` sont en `/documents`, `/tags`, `/activity`, etc. (pas de prefix). Pour les monter sous `/twin/api/*`, le pattern le plus propre est d'utiliser `VITE_API_BASE_URL=/twin/api` au build. C'est compatible avec `client.ts:42` (`buildUrl(path, query)` concatène `BASE_URL + path`).

**Verdict** : compatible avec l'extension `register()` à condition de bake la bonne `VITE_API_BASE_URL`.

### 12.3 — Auth flow

Le `AUTH_TOKEN` est lu de `VITE_AUTH_TOKEN` au build-time. **Pour la prod BNP, c'est inadéquat** :
- Pas de refresh.
- Pas de revocation.
- Pas de challenge MFA / OIDC.

Pour aligner sur OAuth2/mTLS BNP, il faut :
1. Supprimer `VITE_AUTH_TOKEN` du `vite-env.d.ts` (`vite-env.d.ts:5`).
2. Ajouter un `useAuth()` hook qui lit le JWT depuis :
   - Un cookie `httpOnly` SameSite=strict (le plus secure — pas accessible JS donc auto-attaché).
   - OU `sessionStorage` après un flow OIDC redirect (moins secure mais courant).
3. Câbler `apiFetch` pour lire le token au moment du fetch (pas au module-load).
4. Implémenter une logique de 401 → redirect vers IDP.
5. Implémenter un refresh token rotation.

**État actuel** : `AuthorizeDialog` dans ApiTab est un mock-only (`ApiTab.tsx:458-553`) — il met le token dans un state local pour permettre les "Try it out". **Ce n'est pas l'auth flow réel.**

### 12.4 — Multi-workspace claim

Le claim JWT doit contenir `workspace_id` et `palier` (cf. project memory Vihn 2026-05-22 + Geoffrey 2026-05-28 sur le RBAC à designer). Le `CURRENT_USER` hardcodé (`App.tsx:78-82`) doit être remplacé par un `useAuth()` qui décode le JWT et expose `{name, palier, role, workspace_id}`.
