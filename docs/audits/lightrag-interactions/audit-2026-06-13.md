# Audit LightRAG / Twin overlay / WebUI - 2026-06-13

## Verdict court

Le socle storage LightRAG -> Memgraph est le morceau le plus solide du depot:
`register()` ajoute KV, Vector et DocStatus sans fork, patch le backend graph
natif Memgraph, ajoute des batch paths et garde LightRAG comme moteur principal.
Cette couche est coherente avec la doctrine non-fork et reduit bien le travail
local au minimum utile.

Les risques principaux sont au-dessus: routes Twin, shims et frontend promettent
parfois des garanties que LightRAG 1.4.9.11 ne fournit pas nativement, ou
reconstruisent localement une information que LightRAG sait deja produire.

Deux points doivent etre traites comme prioritaires:

1. Les sources de `/twin/api/query` sont encore reconstruites apres coup par une
   deuxieme recherche vectorielle (`_build_sources()`), donc elles ne sont pas
   garanties comme etant le contexte reellement utilise par LightRAG pour
   produire la reponse. LightRAG expose deja `aquery_llm()` et ses references:
   le chemin nominal Twin doit migrer dessus.
2. Le `tag_filter` de retrieval est accepte par l'UI et le backend, mais
   LightRAG 1.4.9.11 ne le connait pas dans `QueryParam` et ne l'applique pas a
   la recherche. C'est un wiring qui a l'air end-to-end mais ne filtre pas la
   retrieval.

Le commit `9c2470d` corrige honnetement la surface visible de TR-RET-02 pour les
reponses `insufficient_information` (`[no-context]` strippe, `answer_status`,
sources masquees). Il ne corrige pas encore le probleme structurel des sources
sur les reponses `grounded`.

## Ce que LightRAG fait deja bien ici

### 1. Storage registry sans fork

`register()` patch les trois registres LightRAG (`STORAGE_IMPLEMENTATIONS`,
`STORAGE_ENV_REQUIREMENTS`, `STORAGES`) pour declarer les backends Memgraph KV,
Vector et DocStatus. Le graph reste `MemgraphStorage` natif LightRAG. C'est le
bon niveau d'intervention: additif, idempotent, peu divergent.

Preuve: `register()` lignes 159-185.

### 2. Pooling Memgraph pragmatique

La separation read/write pools est utile et justifiee: les reads WebUI ne
concurrencent pas les writes d'ingestion. Le handling `bolt://` vs `neo4j://`,
`USE DATABASE`, TLS et timeouts evite beaucoup de code applicatif ailleurs.

Preuve: README lignes 270-293, `_pool.py`.

### 3. Vector backend adapte a Memgraph

Le backend vector:

- cree un index vectoriel et un index id;
- filtre par `cosine_better_than_threshold`;
- auto-recree l'index si Memgraph le signale absent;
- retire le label indexe avant `DETACH DELETE` pour eviter des entrees mortes
  dans l'index vectoriel Memgraph 3.10.

Preuve: `vector_impl.py` lignes 67-151, 187-264, 320-340.

### 4. DocStatus compatible avec les attentes LightRAG

DocStatus stocke `metadata` et `chunks_list` en JSON, puis les deserialise dans
`get_by_id()` parce que `adelete_by_doc_id()` attend un vrai `chunks_list`.
C'est un bon exemple de glue minimale autour de LightRAG au lieu de reecrire la
delete pipeline.

Preuve: `docstatus_impl.py` lignes 163-193.

## Mauvais wiring / mensonges

### C0 - Les sources de `/twin/api/query` ne viennent pas du contexte LightRAG reel

La route Twin execute encore `rag.aquery()`, puis refait une deuxieme recherche
`chunks_vdb.query(query, top_k)` pour construire `sources`.

Depuis LightRAG 1.4.9.11, `aquery()` est seulement un wrapper de compatibilite
autour de `aquery_llm()`: il extrait la reponse texte et jette la structure
retrieval. La route native LightRAG `/query` utilise deja `aquery_llm()` pour
renvoyer la reponse et les references issues du meme pipeline.

Preuves:

- `LightRAG.aquery()` appelle `aquery_llm()` puis ne retourne que le texte.
- `LightRAG.aquery_llm()` renvoie `data`, `metadata` et `llm_response`.
- Route native LightRAG `/query`: `rag.aquery_llm(request.query, param=param)`.
- Route Twin: `rag.aquery(...)` puis `_build_sources(...)`.

Impact:

- Les sources affichees peuvent ne pas etre celles qui ont servi au prompt LLM.
- Les modes `mix`, `hybrid`, rerank, context truncation et graph context peuvent
  diverger de la recherche vectorielle secondaire.
- Les tests actuels peuvent passer tout en validant seulement une projection
  locale, pas la source-of-truth LightRAG.

Etat apres `9c2470d`:

- Corrige pour `insufficient_information`: les sources sont videes et masquees.
- Reste faux pour `grounded`: `_build_sources()` reste le chemin nominal.

Correction recommandee:

1. Migrer `/twin/api/query` vers `rag.aquery_llm()` sur le chemin nominal.
2. Migrer `/twin/api/query/stream` vers le meme contrat, en utilisant
   `llm_response.response_iterator` pour les tokens et `data.references` pour
   les sources finales.
3. Mapper `raw_data.references` / `raw_data.chunks` vers `TwinRetrievalSource`.
4. Garder `_build_sources()` uniquement comme fallback explicite, logge et
   teste, jamais comme chemin nominal.
5. Ajouter un test qui prouve que le chemin `grounded` n'appelle plus
   `chunks_vdb.query()` une deuxieme fois.

### C1 - `tag_filter` retrieval est accepte mais pas applique par LightRAG

Le frontend envoie `tag_filter` depuis Retrieval et ApiTab. Le backend l'ajoute
a `TwinQueryBody`, puis a `QueryParam`. Or LightRAG local `v1.4.9.11` n'a pas de
champ `tag_filter` dans `QueryParam`, et aucun fichier Python LightRAG installe
ne reference `tag_filter`.

Le fallback backend fait seulement:

```python
param = QueryParam(**fallback_kwargs)
setattr(param, "tag_filter", tag_filter)
```

Ce champ dynamique n'est pas lu par LightRAG 1.4.9.11. Les tests actuels
verifient que l'attribut existe, pas que la retrieval change.

Preuves:

- `twin_query_routes.py` lignes 65, 142-159, 517-523.
- `ApiTab.tsx` lignes 70-75 et 620-629 affiche/injecte `tag_filter`.
- LightRAG local: `QueryParam` contient `include_references`, pas `tag_filter`.

Impact:

- L'utilisateur croit filtrer le contexte par tags.
- Le LLM peut repondre avec des chunks hors tags.
- Les sources reconstruites apres coup peuvent accentuer le faux sentiment de
  grounding.

Correction recommandee:

1. Court terme: renommer l'UI en "post-filter sources/data" ou desactiver le
   filtre en retrieval chat avec un badge explicite tant que ce n'est pas
   server-side.
2. Moyen terme: implementer un vrai `tag_filter` dans `MemgraphVectorDBStorage`
   ou dans une couche pre-retrieval en resolvant les doc/chunk ids tagges via
   `(:DocStatus)-[:TAGGED_WITH]->(:WebuiTag)`, puis filtrer les chunks vectors.
3. Test requis: un test integration fake vector store qui prouve que deux docs
   avec embeddings similaires mais tags differents ne renvoient que le doc tagge.

### C2 - `query/data` post-filtre les tags via `metadata.tags`, alors que les tags reels sont des relations graph

Le backend `query/data` post-filtre les rows LightRAG par doc status, puis lit
`metadata.tags`. Mais la route de retag documente et implemente le modele
canonique sous forme de relation:

```cypher
(:DocStatus_{workspace})-[:TAGGED_WITH]->(:WebuiTag_{folder})
```

Donc les tags crees par le WebUI ne sont pas forcement dans
`DocStatus.metadata.tags`, et le filtre `query/data` peut rejeter ou garder les
mauvaises rows selon l'etat historique.

Preuves:

- Filtre `metadata.tags`: `twin_query_routes.py` lignes 288-304.
- Retag par relation graph: `webui_router.py` lignes 1156-1171 et 1301-1314.
- Le list documents, lui, fait bien le join graph: `native_shims.py` lignes
  151-188.

Correction recommandee:

- Factoriser un helper unique `doc_has_tags(doc_id, folder, tag_filter)` base
  sur `TAGGED_WITH`, et l'utiliser dans `query/data`, document list et futurs
  filtres retrieval.

### C3 - Le terme "Sources" reste plus fort que le contrat reel

Tant que C0 n'est pas corrige, le panneau "Sources" indique en pratique des
candidats retrouves par Twin apres coup, pas des citations garanties de la
reponse. Le commentaire du module reconnait deja le compromis: "Sources reflect
retrieval, not necessarily citation."

Preuves:

- Requete secondaire: `twin_query_routes.py` lignes 400-415.
- Reponse construite apres coup: lignes 568-575.

Impact:

- Le libelle UI sur-vend une garantie de grounding.
- Les citations `{cite:N}` / `[N]`, quand elles existent, peuvent ne pas
  correspondre a `source.n`.
- Avec `tag_filter` non applique, le faux sentiment de grounding est amplifie.

Correction recommandee:

- Apres C0, utiliser les references LightRAG natives comme source-of-truth.
- Avant C0, renommer le panneau en "Retrieved context" / "Candidats retrouves"
  si on veut eviter de promettre un grounding non garanti.

### C4 - Folder donne une isolation UX, pas une isolation KB

La documentation est honnete dans le README: workspace LightRAG et Twin Folder
sont deux concepts differents. Le code applique `X-Twin-Folder` aux routes Twin
et au list/chunks/delete documents shim en filtrant `DocStatus.metadata.folder`.
Mais le RAG reste dans le workspace LightRAG courant.

Preuves:

- README lignes 85-129.
- `folder.py` resout le header et l'IdP scope, pas le workspace.
- `native_shims.py` filtre documents par metadata folder lignes 133-148.

Impact:

- Une query LightRAG n'est pas naturellement folder-scoped.
- Les graph endpoints lisent le graph workspace et ne filtrent pas par folder,
  sauf tags/doc labels herites cote frontend.

Correction recommandee:

- Dans l'UI, eviter "KB" pour les folders si cela suggere une base separee.
- Pour une vraie isolation: soit un workspace LightRAG par folder, soit un
  filtre retrieval pre-query robuste par doc/chunk ids.

### C5 - Fallback graph seed peut masquer un backend vide ou casse

`/twin/api/graph/entities` et `/graph/relations` retournent la seed si Memgraph
ne renvoie aucune entite. C'est utile en demo mais risqué en prod: une KB vide,
une mauvaise connexion ou un schema casse peut redevenir une demo silencieuse.

Preuves:

- `webui_router.py` lignes 1612-1626 et 1629-1646.
- Les safeguards empechent deja les seed documents en mode memgraph, mais pas
  ce fallback graph.

Correction recommandee:

- En `webui_stores="memgraph"` ou IdP actif, retourner `[]` ou `503` explicite
  au lieu de seed graph.
- Garder la seed uniquement sous `webui_stores="seed"` ou `VITE_FORCE_MSW=true`.

### C6 - "Read source" promet le texte ingere mais n'appelle aucun endpoint de lecture extrait

`ReadSourceModal` annonce "what the indexer ingested" et "Post-extraction text
used for retrieval", mais affiche `doc.extracted_text` si present, sinon un
placeholder demo. Le document list ne peuple pas `extracted_text` depuis
LightRAG.

Preuves:

- Promesse: `ReadSourceModal.tsx` lignes 1-15.
- Placeholder: lignes 43-46.

Correction recommandee:

- Remplacer par une vue chunks reelle (`/documents/{id}/chunks`) ou changer le
  libelle en "Preview unavailable" tant que le texte extrait complet n'est pas
  stocke.

### C7 - Per-doc scan est un ack/no-op

Le README et le code sont honnetes sur le fait que `POST /documents/{id}/scan`
est un no-op. Le risque est plutot UX: bouton "Re-process" et texte "Pipeline
scan started" peuvent etre interpretes comme une action ciblee.

Preuves:

- README lignes 169-172.
- `native_shims.py` lignes 21-22.
- `App.tsx` lignes 318-337 utilise en fait `/documents/reprocess_failed` dans
  le flux principal.

Correction recommandee:

- Supprimer la route per-doc scan de l'UI ou la laisser uniquement en
  compatibilite API avec libelle "ack only".

### C8 - ApiTab affirme une injection transparente `tag_filter` / `visibility`

L'ApiTab affiche: "gateway transparently injects tag_filter and visibility
scoping". Ce n'est pas vrai pour LightRAG 1.4.9.11: `tag_filter` n'est pas
applique par la query native, et la visibility n'est pas une contrainte
retrieval native.

Preuve: `ApiTab.tsx` lignes 70-75.

Correction recommandee:

- Remplacer par une phrase factuelle: "Twin overlay accepts tag_filter on
  governed endpoints; native LightRAG routes remain upstream-compatible."

## Optimisations pour reduire notre travail

### Garder LightRAG proprietaire de l'ingestion, deletion et pipeline

A ne pas reecrire:

- `/documents/upload`
- `/documents/reprocess_failed`
- `adelete_by_doc_id`
- `aquery_data`
- `pipeline_status`

Le repo fait deja plutot bien cela. Il faut continuer a adapter la forme HTTP
pour le frontend, pas dupliquer la logique.

### Remplacer les shims statiques par des projections minimales

`/openapi` statique est utile pour une visite guidee, mais l'ApiTab utilise deja
`/openapi.json` direct cote frontend. Garder les deux entretient deux verites.
Recommandation: deprecier `/openapi` Twin ou le generer depuis `/openapi.json`.

### Unifier les deux chemins serveur

Il existe:

- `server/app.py`: serveur standalone, instancie son propre `LightRAG`.
- `register(... mount_server=True ...)`: patch du serveur LightRAG hote, capture
  le `LightRAG` hote.

Les deux chemins sont utiles, mais doivent etre documentes comme:

- standalone = tests/dev/integration controlee;
- production = patch hote LightRAG.

Eviter d'ajouter de nouvelles features dans un chemin sans l'autre. Le test
route parity aide, mais il ne couvre pas les differences de lifecycle.

### Faire de `TAGGED_WITH` la source unique des tags

Le code est deja presque la:

- document list lit `TAGGED_WITH`;
- retag ecrit `TAGGED_WITH`;
- graph herite les tags via source docs cote frontend.

Le dernier reste a faire est critique: query filtering doit lire `TAGGED_WITH`
ou ne pas pretendre filtrer.

### Supprimer les seed fallbacks en prod

La doctrine mock-kill est bonne, mais il reste des residus:

- graph fallback seed quand Memgraph vide;
- ReadSource placeholder demo;
- ApiTab mock helpers exportes pour tests.

Recommendation: centraliser une seule condition `is_demo_mode()` cote backend et
refuser toute seed visible si IdP actif ou `webui_stores="memgraph"`.

## Conclusion

Le bon axe d'optimisation n'est pas d'ajouter plus de backend Twin. C'est
l'inverse: laisser LightRAG faire ingestion, deletion, pipeline et retrieval
autant que possible, et n'ecrire localement que les adaptateurs de contrat
necessaires. Aujourd'hui, les endroits dangereux sont ceux ou l'overlay donne
l'impression d'une capacite native LightRAG alors qu'il ne fait qu'accepter un
parametre ou reconstruire une projection apres coup.
