# Validate ingestion responsiveness in a deployment

Issue [#4](https://github.com/menezis-ai/lightrag-memgraph/issues/4) tracks a
historical 502 incident during PDF ingestion. LightRAG 1.5.7's legacy parser
already runs extraction through `asyncio.to_thread`. A pypdf warning or several
concurrent awaits alone do not establish the cause of an HTTP timeout.

The public regression suite exercises that real upstream parser and pypdf with
synthetic valid, duplicate-dictionary and invalid PDFs. While extraction is held
open, `/health` and `/ready` must return JSON within 200 ms; the first probe must
also start within 500 ms of scheduling, catching an event loop that cannot even
start a request. A deliberately inline parser must fail that detector. A separate
thread watchdog releases blocked extraction after 1.5 seconds, including when
asyncio cannot schedule its own timeout. Successful extraction persists through
the actual Memgraph KV adapter; malformed input returns a JSON error through the
HTTP test harness, and subsequent probes remain responsive.

This harness is an in-process ASGI application. It does not exercise nginx, the
BNP-internal pipeline, the original Lexmark scans or an installed BNP deployment.
Those observations remain necessary to resolve the production incident.

## Collect deployment evidence

1. Record the application/image commit, worker count, Python, LightRAG, pypdf,
   adapter and Memgraph versions. Confirm which parser engine and code path the
   actual ingestion pipeline calls. Supporting 1.5.7 in the adapter does not
   upgrade a deployed application by itself.
2. From a separate process, probe both the pod directly and its public/proxied
   address while ingesting. Start probes before ingestion. Use the original
   failing PDFs where available, a valid PDF and a deliberately invalid PDF.
   Keep documents within the authorized environment; capture file identifiers
   or hashes rather than publishing their contents.
3. Repeat with one document and with the deployment's configured concurrency.
   Measure the health response time and event-loop lag throughout the parse,
   extraction, embedding and persistence stages. The public target is health
   responses below 200 ms, including after a parse failure. Adjusting that
   target requires a measured operational reason, not just a larger timeout.
4. Correlate timestamps and request IDs with ingress/nginx upstream timings,
   worker logs, CPU/memory, parser activity and Bolt pool waits. Distinguish a
   blocked loop, resource exhaustion, a connection failure and an ingress
   timeout; each requires different evidence and remediation.
5. Verify that the public path's error responses are handled correctly too.
   An application's JSON exception handler cannot control HTML generated by
   nginx or another upstream proxy.

For example, collect HTTP timings from the same network as the affected caller
in a separate terminal while triggering ingestion through the real application:

```bash
export LIGHTRAG_URL='https://your-deployment.example'
for attempt in $(seq 1 120); do
  date -u '+%Y-%m-%dT%H:%M:%SZ'
  curl --silent --show-error --connect-timeout 2 --max-time 2 \
    --output /dev/null \
    --write-out 'status=%{http_code} content_type=%{content_type} seconds=%{time_total}\n' \
    "$LIGHTRAG_URL/health"
  sleep 0.5
done | tee health-during-ingestion.log
```

Probe `/ready` as well if that endpoint is exposed by the deployment. Preserve
response examples separately to check the JSON schema; a JSON content type alone
does not prove a valid body. The 2-second curl limit bounds the observation; any
response over 200 ms still violates the responsiveness target.

## Apply a fix at the observed blocking stage

If a custom pipeline still invokes synchronous PDF extraction on the event loop,
move that work into a bounded executor or isolated worker. Limit admission to
heavy work separately; an `asyncio.Semaphore` around an inline CPU-heavy call does
not make it asynchronous. `asyncio.wait_for(asyncio.to_thread(...))` timing out
does not terminate the underlying worker thread. Use process isolation when a
hard execution limit is required, and account for work still running after a
client cancellation before admitting more documents.

Re-run the same documents and concurrency after deployment. Record the before
and after timings, absence or persistence of ingestion-correlated 502s, recovery
after failures and the deployed fix's commit. Keep the production incident open
in the pipeline's own tracking until that evidence is collected.

## Run the public regression locally

Against an isolated Memgraph instance with a supported LightRAG 1.5.7 install:

```bash
python -m pip install '.[test]' 'lightrag-hku==1.5.7'
MEMGRAPH_URI=bolt://localhost:7687 python -m pytest -q \
  tests/test_pdf_responsiveness.py --junitxml=reports/pdf.xml
```

JUnit properties retain the probe timings, parse overlap and worker thread IDs.
Older LightRAG profiles explicitly skip this version-specific parser test while
continuing to run their storage compatibility suites.

Sources: [upstream parser](https://github.com/HKUDS/LightRAG/blob/v1.5.7/lightrag/parser/legacy/parser.py#L48),
[Python thread offloading](https://docs.python.org/3/library/asyncio-task.html#asyncio.to_thread)
and [executor shutdown semantics](https://docs.python.org/3/library/concurrent.futures.html#concurrent.futures.Executor.shutdown).
